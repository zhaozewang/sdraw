### FS-001 — No frontend-level intent document  ·  severity: **high**  ·  effort: one-pr

Evidence: neither `frontend/CLAUDE.md`, `frontend/src/CLAUDE.md`, nor any
`.claude/rules/*frontend*.md` exists. The only cross-cutting frontend
doc is the drifted README tree (`README.md:90-119`, already global F-002).

Consequence: this subsystem does 101 commits / 30d across 15k LOC of very
opinionated code (single global Zustand store, manual React Flow + DOM
coupling, dual export renderers, modal-based editors with in-memory run
caches). A reviewer has no written contract for any of:

- Who owns autosave, history, kernel actions, multi-figure distribution,
  Run All, external-conflict resolution — all bundled into `boardStore.ts`.
- Whether components may read `useBoardStore.getState()` directly or must
  subscribe (currently 16 files do the former, mixing subscription and
  snapshot reads — see FS-004).
- Whether `captureCanvas.ts` is live, deprecated, or dead (it's dead; see
  FS-006).
- What the plot/figure data model is (plotCodeId → figureIndex → anchor
  element mapping is implemented in `boardStore.ts:633-697` but
  documented only in comments).

Recommended fix: a 1-page `frontend/CLAUDE.md` with (a) module map of the 35
files grouped by responsibility, (b) the rule "state reads flow through
subscription; `getState()` is allowed only inside store actions and
imperative handlers", (c) a pointer to `board-kernel/SKILL.md` for the
kernel protocol, (d) a list of the 4-5 load-bearing invariants currently
hidden in comments (plotCodeId registry; autosave = render guarantee; delta
save suppresses checkpoint when snapshot exists; figure anchor convention).
Once that's in, most of the findings below become either rule-violations
(measurable) or conventions (intentional).

### FS-004 — `getState()` direct-read pattern spreads without a rule  ·  severity: medium  ·  effort: one-pr (doc)

`useBoardStore.getState()` (synchronous non-reactive read) is called from
16 files outside the store: `App.tsx`, `Canvas.tsx`, `Toolbar.tsx`,
`PlotEditor.tsx`, all 7 node components (`ArrowNode`, `ImageNode`,
`PenNode`, `PlotNode`, `RectangleNode`, `Resizer`, `TextNode`), plus the
hooks (`useAutoSave`, `useKeyboardShortcuts`, `useVSCodeBridge`) and
`captureCanvas.ts`. Many of these are legitimate (event handlers, timers,
imperative DOM), but some are inside React component bodies.

Example that reads stale-at-render: `frontend/src/hooks/useAutoSave.ts:21`
reads `useBoardStore.getState()._savedElementHashes.size > 0` inside an
effect that depends only on `[isDirty, board]`. If that map is updated
without flipping `isDirty`, the effect doesn't re-run — probably fine
today because the map grows on save which does flip `isDirty`, but it's a
subtle coupling no one codified.

This is a convention-gap, not a bug: nothing says whether `getState()`
outside the store is allowed, encouraged, or forbidden. Fix shape: one
section in `frontend/CLAUDE.md` stating "subscribe via hook in render;
`getState()` is allowed only in event handlers, timers, `useEffect`
cleanup, imperative DOM, and inside store actions." Then audit the 16
call-sites against that rule.

Fix: delete lines 172-179.

### FS-006 — Dead export renderer (`captureCanvas.ts`)  ·  severity: medium  ·  effort: one-pr

`frontend/src/utils/captureCanvas.ts` is 397 LOC exporting exactly one
symbol (`captureCanvasForExport` at `:385`). Grep for that name across
`frontend/src` and `backend/` returns exactly one hit — the definition
itself. No caller imports it. The live export path is
`captureOffscreen.ts::captureOffscreen` (called from `App.tsx:903` and
`boardStore.ts` via dynamic import `captureOffscreen.ts:643`). The file's
own comment on `:237` says:

> The primary export path uses captureOffscreen.ts (html2canvas) instead.

This is the in-code shadow of the user's `feedback_export_architecture.md`
memory entry ("dual-renderer approach is fundamentally broken; use same
React components for export"). The user has already made this call in
their notes; the code is midway through the cleanup. 397 lines of
unreachable code in a subsystem that already has the "too-large files"
smell (FS-002) is pure drift — anyone reading the utils folder today has
to read it to learn it's dead.

Fix shape: delete `captureCanvas.ts` and its lone export. If there's
concern about losing the SVG serialization logic, move the file to
`docs/history/` with a header noting "superseded by captureOffscreen +
pre-rasterized text (commit 2f8edf3, 2026-04-??)".

### FS-007 — Home screen bundled into `App.tsx`  ·  severity: medium  ·  effort: one-pr

`App.tsx:537-827` defines `WelcomeScreen` — the recent-boards grid, new-board
card, board card with delete action, empty state, create dialog. It depends
on seven top-level helpers (`getRecentBoards`, `addRecentBoard`,
`removeRecentBoard`, `FileBrowserDialog`, `NewBoardDialog`, `BoardCard`,
`CreateBoardCard`, `DeleteBoardDialog`) also defined in `App.tsx`. This is
~290 LOC that has no relationship to the editor runtime — it's literally
a different screen — and none of it is code-shared with the editor view.

The cost shows up in the lazy-load story: Vite bundles everything in
`App.tsx` into the main chunk, so opening the app pays the CodeMirror
import path (pulled via `Editor` → `PlotEditor` / `SetupEditor`) even if
the user only ever sits on the welcome screen.

Fix: extract `frontend/src/screens/WelcomeScreen.tsx` (and the subcomponents
it alone uses). One PR, no behavior change.

### FS-008 — Ad-hoc `localStorage` keys with no central schema  ·  severity: low  ·  effort: one-pr

Four `localStorage` keys are scattered with inline string literals:

- `'sdraw_recent_boards'` — `App.tsx:38`
- `'sdraw_theme'` — `store/uiStore.ts:119, :135, :142`
- `'sdraw_python_env'` — `store/uiStore.ts:176, :179, :180`
- `'sdraw_recent_colors'` — `components/Inspector/Inspector.tsx:342`

Consequence: typos are free (no key is imported anywhere it's read),
there's no one place to document what each key stores, and no migration
path when a shape changes. Also no sanity check — the `recent_boards`
`JSON.parse` at `App.tsx:43` will crash the tab if a user writes garbage
into that key from devtools, because the `catch` on `:45` silently returns
`[]` only if parse throws; a shape mismatch (parse succeeds but returns a
non-array) would surface later.

Fix shape: one `frontend/src/utils/localStorage.ts` exporting typed
accessors (`getRecentBoards`, `setRecentBoards`, `getTheme`, `setTheme`, …)
with the keys as module-private constants.
